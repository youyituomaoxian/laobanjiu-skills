# LBJ-监督与被监督 · 双模式监督协议

## 模式判别（第一步必须做）

检查调用输入：

- 输入包含 `## 监督交接卡 LBJ-SUP` 起始标记 → 进入 **audit 模式**（监督侧）
- 输入是「生成监督卡 / 输出监督卡 / 交监督卡 / 本轮接受监督」类指令 → 进入 **emit 模式**（执行侧）
- 两者都不满足 → 向用户确认想用哪个模式

---

## 模式 A：emit（执行侧 → 产出交接卡）

**触发时机**：一轮工作完成且包含关键断言（声称全绿/基线数字/文档同步/真源改动/方案待拍板）时，按用户指令生成交接卡。

**生成步骤**：

1. 回顾本轮全部操作，列出**操作清单**（做了什么，编号）。
2. 把本轮所有**主张**翻译成**断言表**——这是核心纪律：
   - 每条断言 = 「断言内容 + 验证命令 + 预期结果」三要素，缺一不可。
   - 事实类主张（数字/状态/门禁结果）必须给可直接执行的验证命令。
   - 无法机器验证的判断类主张（方案取舍/设计推理）单独标注 `[判断]`，放进「方案主张」区，不放断言表。
   - 禁止把模糊措辞（「应该没问题」「基本对齐」）写进断言表。
   - **验证命令必须可执行**：写卡前先在本机真跑一次。跨平台不保证时**双写**（POSIX `wc -l` + Windows PowerShell 等价命令），并附「工具链缺失时的替代通道」（Python 读盘 / PowerShell / 内置检索工具 / `git grep`）。当场跑不通的命令不得留在卡上——给不出可执行命令的事实类主张，降级为 `[判断]` 并写明原因。
3. 附上**证据**：diff 统计（`git diff --stat` 或文件清单）、关键命令输出路径——监督窗口可能没有本对话上下文，证据必须自包含。
   状态类断言（「工作区干净」「零文件改动」）必须**写清口径**：`git status` 只覆盖 tracked 与未被忽略的 untracked，**被 `.gitignore` 忽略的路径（产物目录、过程文档、本地草稿、内部记忆）一律不可见**。正确措辞是「tracked 工作区干净」；若确需断言「零改动」，须额外核对忽略路径（`git status --ignored` 或 mtime 比对）并写明核到了哪些。

**断言纪律（2026-09-22 首轮监督实战沉淀，FAIL 驱动）**：

1. **数字现跑，禁引记忆**：凡数字类断言（行数/字数/计数/SHA/基线/远程状态），验证命令必须现跑现填——禁止从记忆、会话早前输出或旧报告引用数值。`git ls-remote` 等远程状态出卡前必须现查；执行侧自己的长期记忆/笔记里若已有更新值，以现跑为准并交叉核对。
2. **「干净」断言注明口径**：`git status` 只覆盖 tracked 文件，被 `.gitignore` 忽略的路径不在证明范围内——断言措辞写「tracked 文件干净」，不写「绝无改动」。
3. **「全绿」附非阻断计数**：门禁全绿只证明阻断项通过，「全绿」表述必须附带 MEDIUM / 信息性 HIGH / SKIP 计数，防止被解读为「无问题」。
4. **证据强度 ≥ 结论强度**：自报盲区覆盖的主题（如未读原文的机制）禁止下确定性「采纳/不取」结论，只能标「待深读后判定」；对借鉴对象原文的机制描述，须以读到的原文为据，不得凭印象转述。

4. **自报弱点**：诚实写下本轮最可能出错的 1-2 处（不确定的估算、没跑的验证、靠记忆未核实的引用）。不写弱点的卡退回重写。
5. 标注**建议检查点**：CP1 diff 审查 / CP2 门禁复跑 / CP3 批次复核 / CP0 方案反审 / CP4 推送终审。
6. 按下方模板输出完整交接卡（整卡放在一个 markdown 代码块内，方便用户整段复制）。

### 交接卡模板

```markdown
## 监督交接卡 LBJ-SUP
- card_id: SUP-<YYYYMMDD>-<HHmm>
- 项目/工作区: <绝对路径>
- 分支/状态: <分支名 + 未提交文件数；状态口径写明「tracked 干净」或「含 ignored 已核对」，不要泛指「零改动」>
- 操作清单:
  1. …
  2. …
- 断言列表:
  | # | 断言 | 验证命令 | 预期 |
  |---|------|----------|------|
  | A1 | … | … | … |
- 证据:
  - diff: <git diff --stat 输出或文件清单>
  - 其他: <命令输出/文件路径>
- 方案主张（供反审，如无删此节）:
  - [判断] <原话摘录，不转述>
- 自报弱点:
  - …
- 建议检查点: <CP0/CP1/CP2/CP3/CP4，可多选>
## 监督交接卡结束
```

## 模式 B：audit（监督侧 → 执行监督）

**前提纪律**：监督者**只读不改**——不编辑任何文件、不执行任何写操作；结论以监督报告形式输出，交回用户/执行窗口处理。全程对抗立场：任务是**找错**，不是认可。

**执行步骤**：

0. **环境通道检查**（先做）：在跑任何验证命令前，确认卡上给的工具在本机可用（`wc`/`grep`/`ls` 等 coreutils、目标语言运行时、被调用脚本是否存在）。若通道损坏或缺失：
   - **不得**因命令跑不通就把断言判成 `SUSPECT` 或跳过——`SUSPECT` 只留给「口径模糊 / 真无法测量」。
   - 改用**等价通道**重测（Python 读盘计数、PowerShell、内置检索工具、`git grep`），并保持与原命令同口径（见「判级纪律」下表）。
   - 报告中显式声明「原命令在本机不可执行（附报错），判级基于等价测量」——这是**环境免责声明**，不是判级依据。
   - 执行前核实被调用脚本是否**只读**（搜 `writeFileSync` / `execSync` / 重定向等副作用），确认无副作用后再跑门禁；跑完**复测状态类断言**，以佐证门禁本身无副作用。
1. **解析交接卡**：提取断言表、证据、方案主张、项目路径。
2. **逐条断言验证**（CP2 核心）：对断言表每条 A#，实际运行验证命令，实测 vs 预期对比，判级：
   - `PASS` 实测符合预期
   - `FAIL` 实测不符（附实测输出摘录）
   - `SUSPECT` 口径模糊 / 真无法测量（**注意：命令本机跑不通不属此类**，按步骤 0 换等价通道重测）
   - 判 `FAIL` 前必须先做下表的**归因三步**，不得直接收工。
3. **diff 超范围检查**（CP1 核心）：对照操作清单，核实实际改动（git status/diff 或文件系统）——是否有清单外改动（夹带）、清单内声称但实际不存在的改动（虚报）。
4. **方案反审**（CP0，卡含方案主张时）：对每条 `[判断]` 给出**最强反例**或指出其未考虑的成本/风险；给不出反例就明说「未找到反例」，不硬造。
5. **自报弱点核验**：执行侧自报的弱点逐条核实是否属实、是否已构成问题。
6. **输出监督报告**（按下方模板，附「未覆盖区域」声明——监督盲区 = 交接卡没提供的部分）。

### 判级纪律：FAIL 归因三步（先归因，再定级）

实测不符时**不要直接判 FAIL 收工**——先按下表归因，把「为什么不符」写进报告。**归因不改变 FAIL 事实**（断言写「当前」就必须现跑现测），但决定执行侧该怎么修，也决定这条 FAIL 该不该沉淀成规则。

| 步 | 查什么 | 判据 | 处置 |
|----|--------|------|------|
| ① 口径 | 度量口径是否不同 | 行数 vs 非空行、字节 vs 字符、LF vs CRLF、正则转义、含/不含某目录 | 统一口径重测；口径未写明 = **卡本身不合格** |
| ② 快照 | 数字是否与**某个旧提交/旧版本**精确吻合 | 遍历近期提交（`git show <rev>:<file>` / `git grep <rev>`）或旧版本重测，命中即判定 | 判 FAIL，但归因为**引用基线过期**而非编造 |
| ③ 环境 | 命令能否本机执行、是否受依赖/路径/换行干扰 | 退出码 127、缺依赖、CRLF、沙箱拦截 | 换等价通道重测，报告附环境免责声明 |

**反模式（务必避免）**：把「与旧快照精确吻合」的数字当作「凭空编造」上报——同源失真必须**归并为一条根因**（典型：引用基线整体停留在旧提交 X，真实 HEAD 已是 Y），而不是拆成多个独立错误逐个追责。归并后还要**横向排查同期其它数字是否同源失真**（往往一条根因解释多条 FAIL）。

**沉淀判据**：归因落在②时，几乎必然暴露系统性缺口——「数字类断言靠记忆而非现跑」。应作为规则回灌执行侧（见闭环规则 3），而不是只修这一次。

```markdown
## 监督报告 LBJ-SUP-AUDIT
- 对应卡: <card_id>
- 环境通道: <原命令可执行 / 不可执行（附报错）+ 替代通道与等价口径>
- 断言验证:
  | # | 结果 | 实测摘要 |
  |---|------|----------|
  | A1 | PASS/FAIL/SUSPECT | … |
- FAIL 归因: <逐条归因（口径/快照/环境）+ 同源归并结论>
- diff 审查: <一致 / 夹带：… / 虚报：…；状态类断言的覆盖口径与盲区>
- 方案反例: <最强反例或「未找到反例」>
- 自报弱点核验: <属实并成立 / 属实但无实害 / 不成立>
- 遗留风险: …
- 未覆盖区域: <交接卡未提供、无法监督的部分>
## 监督报告结束
```

## 闭环规则

1. 监督报告由**用户**交回执行窗口；执行侧对每条 FAIL/SUSPECT 必须回应：修复、反证、或接受并说明理由——不许无视。
2. 监督结论与处置结果写入**执行窗口的项目记忆日志**（留痕纪律：监督无痕迹 = 没监督）。
3. 反复出现的同类 FAIL → 归因为规则缺口，沉淀进该项目门禁/规则（能机器化的监督优先于模型互查——L0 > L1 > L2 > L3）。已识别的高频缺口与对应沉淀形式：
   - **数字类断言引用记忆值而非现跑**（表现为断言值与旧提交/旧版本精确吻合）。沉淀形式：数字类断言写卡前必须现跑一次；确需引用时，「预期」栏须标注来源与测量时间。
   - **「工作区干净」类断言的忽略路径盲区**。沉淀形式：状态类断言写明口径（tracked / 含 ignored），必要时补 `git status --ignored` 或 mtime 比对。
   - **验证命令本机不可执行**。沉淀形式：命令入卡前先自测；跨平台不保证时双写（POSIX + PowerShell）并附替代通道。

## 检查点对照（交接卡「建议检查点」字段含义）

| CP | 名称 | 监督重点 | 典型时机 |
|----|------|----------|----------|
| CP0 | 方案反审 | 判断类主张找反例 | 拍板前 |
| CP1 | diff 审查 | 超范围/夹带/虚报 | 每轮改完文件 |
| CP2 | 门禁复跑 | 断言表逐条验证 | 声称「全绿/0 HIGH/数字成立」 |
| CP3 | 批次复核 | 台账漏项/误判 | 大批次（盘点→拍板前） |
| CP4 | 推送终审 | 推送范围核对 | commit/push 前 |
