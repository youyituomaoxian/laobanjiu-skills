# LBJ-监督与被监督 · 双模式监督协议

## 模式判别（第一步必须做）

检查调用输入：

- 输入包含 `## 监督交接卡 LBJ-SUP` 起始标记 → 进入 **audit 模式**（监督侧）
- 输入是「生成监督卡 / 输出监督卡 / 交监督卡 / 本轮接受监督」类指令 → 进入 **emit 模式**（执行侧）
- 两者都不满足 → 向用户确认想用哪个模式

---

## 模式 A：emit（执行侧 → 产出交接卡）

**触发时机**：一轮工作完成且包含关键断言（声称全绿/基线数字/文档同步/真源改动/方案待拍板）时，按用户指令生成交接卡。

**生成步骤**：

1. 回顾本轮全部操作，列出**操作清单**（做了什么，编号）。
2. 把本轮所有**主张**翻译成**断言表**——这是核心纪律：
   - 每条断言 = 「断言内容 + 验证命令 + 预期结果」三要素，缺一不可。
   - 事实类主张（数字/状态/门禁结果）必须给可直接执行的验证命令。
   - 无法机器验证的判断类主张（方案取舍/设计推理）单独标注 `[判断]`，放进「方案主张」区，不放断言表。
   - 禁止把模糊措辞（「应该没问题」「基本对齐」）写进断言表。
3. 附上**证据**：diff 统计（`git diff --stat` 或文件清单）、关键命令输出路径——监督窗口可能没有本对话上下文，证据必须自包含。
4. **自报弱点**：诚实写下本轮最可能出错的 1-2 处（不确定的估算、没跑的验证、靠记忆未核实的引用）。不写弱点的卡退回重写。
5. 标注**建议检查点**：CP1 diff 审查 / CP2 门禁复跑 / CP3 批次复核 / CP0 方案反审 / CP4 推送终审。
6. 按下方模板输出完整交接卡（整卡放在一个 markdown 代码块内，方便用户整段复制）。

### 交接卡模板

```markdown
## 监督交接卡 LBJ-SUP
- card_id: SUP-<YYYYMMDD>-<HHmm>
- 项目/工作区: <绝对路径>
- 分支/状态: <分支名 + 未提交文件数或「干净」>
- 操作清单:
  1. …
  2. …
- 断言列表:
  | # | 断言 | 验证命令 | 预期 |
  |---|------|----------|------|
  | A1 | … | … | … |
- 证据:
  - diff: <git diff --stat 输出或文件清单>
  - 其他: <命令输出/文件路径>
- 方案主张（供反审，如无删此节）:
  - [判断] <原话摘录，不转述>
- 自报弱点:
  - …
- 建议检查点: <CP0/CP1/CP2/CP3/CP4，可多选>
## 监督交接卡结束
```

## 模式 B：audit（监督侧 → 执行监督）

**前提纪律**：监督者**只读不改**——不编辑任何文件、不执行任何写操作；结论以监督报告形式输出，交回用户/执行窗口处理。全程对抗立场：任务是**找错**，不是认可。

**执行步骤**：

1. **解析交接卡**：提取断言表、证据、方案主张、项目路径。
2. **逐条断言验证**（CP2 核心）：对断言表每条 A#，实际运行验证命令，实测 vs 预期对比，判级：
   - `PASS` 实测符合预期
   - `FAIL` 实测不符（附实测输出摘录）
   - `SUSPECT` 无法验证/命令报错/预期写得太模糊无法判定——不硬判
3. **diff 超范围检查**（CP1 核心）：对照操作清单，核实实际改动（git status/diff 或文件系统）——是否有清单外改动（夹带）、清单内声称但实际不存在的改动（虚报）。
4. **方案反审**（CP0，卡含方案主张时）：对每条 `[判断]` 给出**最强反例**或指出其未考虑的成本/风险；给不出反例就明说「未找到反例」，不硬造。
5. **自报弱点核验**：执行侧自报的弱点逐条核实是否属实、是否已构成问题。
6. **输出监督报告**（按下方模板，附「未覆盖区域」声明——监督盲区 = 交接卡没提供的部分）。

### 监督报告模板

```markdown
## 监督报告 LBJ-SUP-AUDIT
- 对应卡: <card_id>
- 断言验证:
  | # | 结果 | 实测摘要 |
  |---|------|----------|
  | A1 | PASS/FAIL/SUSPECT | … |
- diff 审查: <一致 / 夹带：… / 虚报：…>
- 方案反例: <最强反例或「未找到反例」>
- 自报弱点核验: <属实并成立 / 属实但无实害 / 不成立>
- 遗留风险: …
- 未覆盖区域: <交接卡未提供、无法监督的部分>
## 监督报告结束
```

## 闭环规则

1. 监督报告由**用户**交回执行窗口；执行侧对每条 FAIL/SUSPECT 必须回应：修复、反证、或接受并说明理由——不许无视。
2. 监督结论与处置结果写入**执行窗口的项目记忆日志**（留痕纪律：监督无痕迹 = 没监督）。
3. 反复出现的同类 FAIL → 归因为规则缺口，沉淀进该项目门禁/规则（能机器化的监督优先于模型互查——L0 > L1 > L2 > L3）。

## 检查点对照（交接卡「建议检查点」字段含义）

| CP | 名称 | 监督重点 | 典型时机 |
|----|------|----------|----------|
| CP0 | 方案反审 | 判断类主张找反例 | 拍板前 |
| CP1 | diff 审查 | 超范围/夹带/虚报 | 每轮改完文件 |
| CP2 | 门禁复跑 | 断言表逐条验证 | 声称「全绿/0 HIGH/数字成立」 |
| CP3 | 批次复核 | 台账漏项/误判 | 大批次（盘点→拍板前） |
| CP4 | 推送终审 | 推送范围核对 | commit/push 前 |
